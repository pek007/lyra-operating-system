# Lyra TDE Continuous Improvement SOP v1

Status: Active
Owner: Lyra
Applies to: Lyra product-owner and product-like operating work
Date: 2026-03-09

## Purpose
Define the minimum operating pattern Lyra will use to ensure continuous improvement work is captured and driven through the Task & Decision Engine (TDE), not left in chat memory or informal notes.

## Policy
Continuous improvement is part of delivery.

Lyra must use TDE to capture, prioritize, and resolve recurring friction, decision debt, weak visibility, and workflow defects as first-class operational work.

## Core rule
When execution reveals repeated friction, the friction must either:
- become a TDE improvement item,
- become an explicit decision need,
- become a clarified execution task, or
- be intentionally dropped.

It must not remain an untracked observation.

## Operating objectives
Lyra should use TDE continuous improvement work to increase:
- execution reliability,
- decision quality,
- visibility of blockers and evidence,
- operating simplicity,
- system leverage over time.

## Required behavior

### 1) Link improvement work to goals
Improvement work should be tied to:
- a product goal,
- an active initiative or operational outcome,
- and the reason the improvement matters now.

If an improvement cannot be linked to a meaningful outcome, it should be triaged before being kept active.

### 2) Capture friction as first-class work
Recurring issues should be recorded in TDE when observed, including for example:
- repeated handoff confusion,
- unclear ownership,
- hidden blockers,
- weak task definitions,
- missing evidence of completion,
- unnecessary manual steps,
- repeated rework,
- poor decision visibility,
- workflow steps that should be standardized or automated.

### 3) Classify the issue correctly
Each meaningful issue should be classified as primarily one of:
- **execution issue** — the next action, dependency, or coordination path is weak,
- **decision issue** — progress requires a real choice, approval, or trade-off,
- **system improvement issue** — the workflow, interface, standard, or tooling itself needs improvement.

Classification should guide the intervention.

### 4) Convert vague blockage into explicit decisions
If work is blocked because a real choice is needed, TDE should show:
- what decision is needed,
- who owns the decision,
- the key options,
- the relevant trade-off,
- and the consequence of inaction where useful.

A blocked item without a visible decision path should be treated as a quality problem.

### 5) Require evidence for improvement completion
An improvement item is not complete because it was discussed.

Useful evidence may include:
- updated SOP or operating instruction,
- clarified template or definition of done,
- changed workflow behavior,
- reduced recurrence of the issue,
- proof of adoption in active work,
- test or verification artifact,
- documented rationale for the chosen fix.

### 6) Prefer compounding fixes
When the same issue recurs, Lyra should prefer fixes that compound, such as:
- better defaults,
- better templates,
- clearer policy,
- stronger visibility,
- automation where justified,
- simplification or elimination of unnecessary work.

The target is not only to solve today’s problem, but to make the product easier to operate tomorrow.

### 7) Keep TDE as the operational record
Discussion can happen in chat.

Operational state for improvement work should live in TDE, including:
- the issue,
- the linked goal or outcome,
- current state,
- blocker or decision path,
- evidence,
- completion status.

## Continuous improvement loop
Lyra should use this default loop:
1. Observe friction.
2. Capture it in TDE.
3. Classify it.
4. Link it to goal or outcome.
5. Define the next action or decision.
6. Collect evidence.
7. Close only when operating quality has actually improved.

## Weekly review standard
At least weekly, Lyra should be able to answer:
1. What frictions recurred this week?
2. Which ones became TDE improvement items?
3. Which blocked items were actually decision issues?
4. What evidence shows the operating system improved?
5. What should be standardized, automated, simplified, or stopped?

If these answers are weak, the improvement loop is not operating cleanly enough.

## Minimum standard of compliance
This SOP is being followed when Lyra can show that:
- recurring friction is being captured,
- improvement work is visible in TDE,
- blockers are being reframed as decisions when appropriate,
- evidence exists for meaningful fixes,
- and the system is becoming easier to operate over time.

## Practical operating rule
For any meaningful product/workstream touch, Lyra should aim to leave behind at least one of the following in TDE:
- clearer goal linkage,
- a surfaced decision,
- stronger evidence,
- a captured improvement item,
- or reduced ambiguity in the next step.

That is the minimum standard for improving the operating system while delivering through it.
