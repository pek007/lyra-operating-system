# Lyra OS Structure Direction v1

Status: Draft active direction
Owner: Peter / Lyra
Date: 2026-03-11

## Purpose
Capture the current structural direction for Lyra OS after reviewing the latest deep research on product structure.

This note does not force a portfolio reorganization now.
It clarifies:
- how to interpret the current 7-product model
- where the strongest overlaps are
- what future convergence might look like
- what should happen now versus later

## Current operating model
Lyra OS currently operates through 7 products in order to preserve explicit ownership during an early but rapidly maturing phase:
- Control Panel
- Task Management
- Security
- Improvement
- Delivery
- Interfaces
- Governance

This model remains valid for current operations.

## What the latest structural review suggests
The current seven-product setup is directionally sound, but some products are stronger operating units than others.

Strong current operating units:
- Task Management
- Security
- Delivery
- Control Panel

More overlapping / less mature current units:
- Improvement
- Interfaces
- Governance

The strongest overlaps are:
- Governance <-> Security
- Interfaces <-> Delivery
- Improvement <-> Task Management

## Capability-plane interpretation
The latest structural lens suggests Lyra OS is likely converging toward a smaller number of capability planes over time:
- control plane
- work/execution plane
- delivery/integration plane
- operator experience plane

This is a useful long-term interpretation, but it should currently be treated as a convergence hypothesis rather than an immediate reorg order.

## Direction for now
### Keep the 7-product model operationally
No immediate portfolio merge/re-ID/restructure is required.

### Strengthen product charters now
Immediate work should focus on sharpening the weaker/overlapping products so that:
- Governance clearly owns system rules, decision rights, and coherence
- Interfaces clearly owns contracts, packaging, connectors, and boundary/export mechanics
- Improvement clearly owns the closed-loop learning/prevention mechanism rather than canonical execution state

### Use convergence as a future hypothesis
The likely long-term shape may be fewer products, potentially converging toward:
- Platform Control Plane
- Work Orchestration
- Delivery & Integrations
- Operator Experience

But future convergence should happen only when:
- boundaries are clearer in practice
- mature products have proven their natural operating fit
- simplification reduces ambiguity more than it disrupts continuity

## Immediate rule
Sharpen definitions first. Merge later only if evidence shows a clearer, stronger operating model.

## Long-term design intent
The long-term goal is not merely fewer product boxes.
It is a portfolio where each product is:
- a real operating unit
- clearly bounded
- low in overlap
- strong enough to compound capability over time

## Short rule
**Preserve current ownership continuity now; use stronger product definitions and evidence to determine later convergence.**
